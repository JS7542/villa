# Kangsph 운영 기준과 기존 DB 이전 절차

Kangsph를 개발하면서 정리한 초기 설정, 기존 MySQL DB 이전, 배포, 백업 및 장애 대응 절차입니다.
가족용 서비스에 필요한 관리자 역할과 예약 데이터 보호를 중심으로 운영 기준을 정했습니다.

**Render + Supabase 무료 배포에는 [무료 배포 문서](DEPLOYMENT_FREE.md)를 적용합니다.**
이 문서의 MySQL·Nginx·RDS 관련 내용은 기존 환경을 위한 절차이며, 무료 구성에 RDS나 유료 백업을 추가하는 것은 아닙니다.

현재 구현 범위는 가족 시범 운영용 서비스입니다.
실제 정원, 운영자와 대리 운영자, 이용 수칙, 개인정보 보관·삭제 절차, 백업 복원 검증은 서비스 개시 전에 확인할 항목으로 관리합니다.
아래 내용은 운영 절차를 정리한 것으로, 실제 배포나 기존 DB 이전을 완료했다는 의미는 아닙니다.

## 새 MySQL 환경 구성

빈 DB에서 서비스를 시작할 때 필요한 설정과 최초 관리자 생성 절차를 구성했습니다.
관리자 기본 비밀번호는 두지 않고, 초기 실행 시 환경변수로 전달하도록 구현했습니다.

1. Java 21과 MySQL 8.4를 준비하고 빈 전용 DB 스키마를 사용합니다.
2. `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 환경변수로 설정합니다.
3. `VILLA_MAX_GUESTS`에 시설의 실제 허용 정원을 입력합니다. 기본값 `0`에서는 신규 예약을 차단합니다.
4. 최초 실행에서만 `BOOTSTRAP_ENABLED=true`, `BOOTSTRAP_LOGIN_ID`, `BOOTSTRAP_PASSWORD`를 설정합니다. 비밀번호는 12자 이상, UTF-8 72바이트 이하로 지정합니다.
5. `./gradlew bootRun` 또는 빌드한 JAR로 앱을 실행합니다. 첫 실행에서 Flyway가 스키마를 구성하고, bootstrap 설정에 따라 최초 관리자 계정을 생성합니다.
6. 관리자 생성과 로그인을 확인한 뒤 다음 기동 전에 bootstrap을 비활성화하고 ID·비밀번호 환경변수를 제거합니다. 계정이 있는 DB에서 bootstrap이 활성화되어 있으면 기동을 거절하도록 구현했습니다.
7. 운영 환경에서는 HTTPS와 `COOKIE_SECURE=true`를 유지합니다. 로컬 HTTP 테스트에서만 `false`를 사용합니다.
8. 신뢰할 수 있는 보조 운영자가 초대 가입과 승인을 마치면 관리 화면에서 관리자로 지정합니다. 권한 변경 후에는 다시 로그인해야 하며, 마지막 활성 관리자는 해제·정지할 수 없도록 보호했습니다.

Windows PowerShell에서는 `.\gradlew.bat bootRun`으로 실행합니다.

DB 런타임 계정과 마이그레이션 계정은 분리하는 것을 운영 기준으로 정했습니다.
런타임 계정에는 DML 권한을, Flyway 계정에는 스키마 변경 권한을 부여합니다.
운영 환경의 `spring.flyway.user`, `spring.flyway.password`는 별도 비밀 설정으로 주입합니다.

## v1.0 기존 DB 이전

기존 회원과 비밀번호 해시를 유지하면서 새 스키마와 인증 방식으로 전환할 수 있도록 이전 절차를 정리했습니다.
실제 데이터에 적용하기 전에 별도 복원본에서 구조와 동작을 확인하는 방식입니다.

**기존 DB에 자동 baseline이나 `ddl-auto=update`를 적용하지 않습니다.**

1. 서비스 쓰기를 중지하고 전체 백업과 별도 복원본을 만듭니다. 기존 프로그램 버전, 테이블 행 수, 관리자 계정을 기록합니다.
2. 복원본의 `users`·`invite_codes` 구조를 `V1__legacy_schema.sql`과 대조합니다. 다른 테이블·컬럼·제약이 있으면 먼저 별도 이전 스크립트를 작성합니다.
3. 로그인 ID의 대소문자 중복, 앞뒤 공백, 허용 문자, 비교 collation을 검사합니다. 새 가입은 소문자·trim으로 정규화하며, 기존 ID를 변경해야 하면 당사자와 합의합니다. 기존 로그인 조회 결과는 DB collation에 따라 달라질 수 있습니다.
4. 기존 시각이 한국 현지 시간으로 저장되었는지 확인합니다. 새 버전은 UTC 의미로 사용하므로 필요한 경우 복원본에서 UTC로 변환합니다. 시간대가 불분명한 데이터는 임의로 변환하지 않습니다.
5. 구조가 일치하는 것으로 확인한 복원본에만 운영자가 Flyway baseline version 1을 **명시적으로 실행**합니다. 이후 V2~V4를 적용하며, 게시판이 포함된 버전에서는 V5까지 적용합니다.
6. V3는 기존 초대코드를 SHA-256 해시로 변환하고, 미사용 `ACTIVE` 코드는 폐기합니다. 사용 이력은 유지하고 관리자는 새 초대코드를 발급합니다.
7. 기존 BCrypt 비밀번호 해시와 회원 PK는 유지합니다. 인증을 JWT에서 서버 세션으로 변경했으므로 모든 사용자가 다시 로그인해야 합니다.
8. 복원본에서 로그인, 관리자 승인, 예약·취소, 동시성 테스트를 수행한 뒤 실제 이전 일정을 정합니다.
9. 운영 DB 이전에서도 검증한 절차를 반복하고 원본 백업을 보관합니다. 앱 이미지 롤백과 DB 복원은 별도 작업으로 관리합니다.

## Docker와 Nginx 배포

앱을 Docker 이미지로 빌드할 수 있도록 `Dockerfile`을 구성했습니다.
DB 주소와 비밀값은 이미지에 포함하지 않고 실행 환경에서 전달합니다.
이미지는 `docker build -t villa:review .`로 빌드하며, 앱은 UID `10001`로 실행합니다.

Nginx를 사용하는 환경의 배포 기준은 다음과 같습니다.

- 예시 Nginx 설정의 도메인과 인증서 경로를 실제 값으로 변경합니다.
- 앱 포트 `61228`은 localhost 또는 비공개 네트워크에만 노출합니다.
- DB는 앱에서만 접근할 수 있도록 제한합니다.
- Nginx와 앱의 전달 헤더 처리는 신뢰할 프록시 범위를 정한 뒤 설정합니다.
- 요청 제한은 검증된 `remoteAddr`를 기준으로 적용합니다. 프록시 설정에 따라 여러 사용자의 요청이 같은 주소로 합산될 수 있으므로 공개 전에 신뢰 프록시 설정과 엣지 요청 제한을 검증합니다.

CI는 빌드와 MySQL·PostgreSQL 통합 테스트를 수행하도록 구성했으며, 자동 배포는 포함하지 않았습니다.
배포에는 테스트한 동일 이미지를 사용하고, DB 마이그레이션과 롤백 호환성을 확인하는 절차를 두었습니다.

## 백업과 복구

아래 기준은 **기존 RDS 환경에 적용할 초기 운영안**입니다.
Render + Supabase 무료 구성의 로컬 백업과 복원은 [무료 배포 문서](DEPLOYMENT_FREE.md)의 절차로 구분했습니다.

- RDS 자동 백업 보관 기간은 초기안으로 7일을 두고, 실제 복구 가능 시점을 확인합니다.
- 스키마 변경 직전에는 수동 스냅샷을 생성합니다.
- 백업 파일이나 스냅샷의 존재만으로 복구 가능하다고 판단하지 않고, 격리된 DB에 실제 복원해 확인합니다.
- 복원 후 `users`·`reservations`·`calendar_occupancy`·이력 데이터의 건수와 기간을 대조합니다.
- 목표는 RPO 1시간·RTO 4시간으로 두되, 측정 전에는 보장 수치로 사용하지 않습니다. 월 1회 복원 훈련 기록을 남깁니다.
- 탈퇴·개인정보 삭제 이력을 복원 DB에 다시 적용한 뒤 가족에게 접근을 개방합니다.

## 장애 대응

예약 데이터의 일관성을 확인한 뒤 서비스를 다시 여는 것을 복구 기준으로 정했습니다.

1. 오류, DB 연결, 저장공간을 확인합니다. 예약 쓰기 결과가 불확실하면 앱을 점검 상태로 전환합니다.
2. 가족 연락 경로로 장애 상태를 안내합니다. 메신저로 받은 요청은 임시 접수로만 기록하며 예약을 확정하지 않습니다.
3. 이전 이미지 롤백 또는 별도 DB 복원 후 최근 예약·취소·변경 이력을 대조합니다.
4. 복구 후 미확인 변경 통지를 처리하고, 데이터 유실 여부와 재발 방지 조치를 기록합니다.

상태 확인은 앱 생존 여부와 DB 준비 상태로 나누어 구현했습니다.

| 경로 | 확인 내용 |
| --- | --- |
| `/health` | 프로세스 생존 확인. DB 연결 정상 여부를 의미하지 않음 |
| `/health/ready` | 앱 계정으로 잠금 테이블 조회. 정상 `200`, DB 장애·스키마·권한 문제는 상세 정보를 숨긴 `503` |

외부 HTTPS 감시와 DB 연결·오류율·복구 가능 시점 감시는 앱의 헬스 체크와 별도로 구성해야 할 운영 항목으로 두었습니다.

## 현재 구현 범위와 후속 작업

### 알림과 세션

외부 메시지 자동 발송은 구현 범위에서 제외하고, 관리자가 직접 연락한 뒤 연락 여부와 사용자 확인 상태를 기록하는 방식으로 구성했습니다.
세션과 요청 제한은 단일 JVM 메모리에서 관리하므로 재기동 후에는 다시 로그인해야 합니다. 현재 구조는 다중 앱 인스턴스 운영을 지원하지 않습니다.

### 개인정보 처리

휴면·탈퇴 계정의 개인정보 삭제, 보관 기간 만료 삭제, 복원 후 삭제 이력 재적용은 운영 절차로 처리해야 합니다.
`WITHDRAWN`은 서비스 접근을 차단한 상태이며 개인정보 삭제 완료를 의미하지 않습니다.
개인정보 보관 기간과 삭제 절차는 실제 운영 전에 확정할 항목으로 남겨두었습니다.

### 예약 정책과 관리 화면

예약 제한은 계정 기준으로 적용했습니다. 가족별 쿼터, 추첨, 결제, 다중 숙소는 현재 범위에 포함하지 않았습니다.
정원 외의 초기 규칙인 90일 이내 예약, 연속 3일, 진행 중·미래 예약 2건은 가족 합의 후 설정을 확정합니다.

관리 목록은 200~500건으로 제한했습니다.
점검 일정은 활성 상태를 우선 표시하고, 연락·확인 목록은 미처리 항목 중 오래된 건부터 표시합니다. 처리하면 다음 항목이 나타납니다.
월 캘린더 기간 조회에는 이 제한을 적용하지 않습니다.
장기간 운영에 필요한 관리 목록 페이지 나누기와 아카이브 화면은 후속 개선 항목으로 두었습니다.

### 실제 운영 검증

관리자 추가 인증, 외부 상태 감시, 실제 백업 복원, AWS 배포 검증은 코드 테스트와 별도로 확인해야 할 항목입니다.
구현한 기능과 실제 운영에서 검증한 범위를 구분해 기록하고, 남은 항목을 확인한 뒤 운영 범위를 확대할 계획입니다.
