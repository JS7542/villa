# 운영과 기존 DB 이전

이 브랜치는 가족 시범 운영용 구현이다. 클라우드에 배포하거나 기존 DB를 변경하지 않았다.
실제 정원, 운영자·대리 운영자, 이용 수칙, 개인정보 보관·삭제 절차와 복원 훈련을 완료한 뒤 서비스를 개시한다.

## 새 환경

1. Java 21, MySQL 8.4를 준비한다. DB는 빈 전용 스키마를 사용한다.
2. `DB_URL`, `DB_USERNAME`, `DB_PASSWORD`를 환경변수로 주입한다.
3. `VILLA_MAX_GUESTS`에 시설의 실제 허용 정원을 입력한다. 기본값 0은 신규 예약을 차단한다.
4. 최초 한 번만 `BOOTSTRAP_ENABLED=true`, `BOOTSTRAP_LOGIN_ID`, `BOOTSTRAP_PASSWORD`를 설정한다. 비밀번호는 12자 이상, UTF-8 72바이트 이하이다.
5. `./gradlew bootRun` 또는 빌드한 JAR를 실행한다. 첫 실행에서 Flyway가 스키마와 관리자 계정을 만든다.
6. 다음 기동 전에 bootstrap 설정과 비밀번호를 제거한다. 계정이 있는 DB에서 bootstrap이 켜져 있으면 안전하게 기동을 거절한다.
7. 운영은 HTTPS와 `COOKIE_SECURE=true`를 유지한다. 로컬 HTTP 시험에만 false로 설정한다.
8. 신뢰할 보조 운영자가 초대 가입·승인을 마치면 관리 화면에서 관리자로 지정한다. 권한 변경 후 다시 로그인해야 하며 마지막 활성 관리자는 해제·정지할 수 없다.

DB 런타임 계정은 DML 권한만, Flyway 계정은 스키마 변경 권한을 부여한다. 운영에서는
`spring.flyway.user`, `spring.flyway.password`를 별도 비밀 설정으로 주입한다.

## v1.0의 기존 DB 이전

**기존 DB에 자동 baseline이나 ddl-auto=update를 켜지 않는다.**

1. 서비스 쓰기를 중지하고 전체 백업과 별도 복원본을 만든다. 기존 프로그램 버전·행 수·관리자 계정을 기록한다.
2. 복원본의 users/invite_codes 구조를 `V1__legacy_schema.sql`과 대조한다. 다른 테이블이나 컬럼, 제약이 있으면 먼저 별도 이전 스크립트를 설계한다.
3. 로그인 ID는 새 가입 시 소문자·trim으로 정규화된다. 기존 대소문자 중복·공백·허용 문자·비교 collation을 검사하고 당사자와 변경을 합의한다. 기존 로그인은 DB collation에 따라 조회 결과가 달라질 수 있다.
4. 기존 시각이 한국 현지 시간으로 저장됐는지 조사한다. 새 버전은 UTC 의미로 사용하므로, 그렇다면 복원본에서 기존 값을 UTC로 변환한다. 시각대가 불분명한 데이터를 임의 변환하지 않는다.
5. 구조가 일치한다고 확인한 복원본에만 운영자가 Flyway baseline version 1을 **명시적으로** 실행한다. 이후 새 버전의 V2~V4를 적용한다.
6. V3는 기존 초대코드를 SHA-256 해시로 바꾸고 미사용 ACTIVE 코드는 폐기한다. 관리자에게 새 초대 발급을 안내한다. 사용 이력은 남긴다.
7. 기존 BCrypt 비밀번호와 회원 PK는 유지한다. JWT 방식은 종료되므로 모든 사용자가 다시 로그인해야 한다.
8. 복원본에서 로그인·관리자 승인·예약·취소·동시성 테스트를 수행한 뒤 실제 이전 일정을 잡는다.
9. 운영 이전 시에도 같은 절차를 반복하고 원본 백업을 보관한다. 앱 이미지만 되돌리는 것과 DB 복원은 다른 작업이다.

## 배포

`Dockerfile`은 이미지 빌드용이다. DB 주소·비밀은 이미지에 넣지 않는다.
`docker build -t villa:review .`로 만들 수 있으며 앱은 UID 10001로 실행된다.
예시 Nginx 설정의 도메인·인증서 경로를 실제 값으로 바꾼다.
앱 61228은 localhost 또는 비공개 네트워크에만 노출하고 DB는 앱에서만 접근하도록 한다.
Nginx와 앱의 전달 헤더 처리는 신뢰할 프록시 범위를 정한 뒤 설정한다.
현재 요청 제한은 실제 remoteAddr 기준이므로 프록시 뒤에서는 같은 주소로 합산될 수 있다.
인터넷 공개 전 신뢰 프록시 설정과 엣지 제한을 검증한다.

CI는 빌드·MySQL 통합 테스트만 수행하고 자동 배포하지 않는다.
배포 전 같은 이미지를 테스트하고 마이그레이션·롤백 호환성을 확인한다.

## 백업과 복구

- RDS 자동 백업 보관 7일을 초기안으로 설정하고 복구 가능 시점을 모니터링한다.
- 스키마 변경 직전 수동 스냅샷을 만든다. 백업의 존재만으로 성공으로 보지 않는다.
- 격리 DB로 실제 복원한 뒤 users/reservations/calendar_occupancy/history 건수와 기간을 대조한다.
- 목표 RPO 1시간·RTO 4시간은 측정 전 보장 수치가 아니다. 월 1회 복원 훈련 기록을 남긴다.
- 복원 시 탈퇴·삭제 이력을 다시 적용한 뒤 가족에게 접근을 개방한다.

## 장애 대응

1. 오류·DB 연결·저장공간을 확인하고 예약 쓰기가 불확실하면 앱을 점검 상태로 전환한다.
2. 가족 연락 경로에 상태를 안내한다. 메신저 접수는 임시 접수이며 확정하지 않는다.
3. 이전 이미지 롤백 또는 별도 DB 복원 후 최근 예약·취소·변경 이력을 대조한다.
4. 복구 후 미확인 변경 통지를 처리하고 유실 여부와 재발 방지 조치를 기록한다.

`/health`는 프로세스 생존 확인이며 DB readiness를 뜻하지 않는다.
외부 HTTPS 감시와 DB 연결·오류율·복구 가능 시점 감시는 별도로 구성한다.

## 현재 한계 / 정식 운영 전

- 자동 외부 알림 대신 관리자 직접 연락과 연락·사용자 확인 기록을 사용한다.
- 단일 JVM 메모리 세션과 요청 제한을 쓴다. 재기동 시 재로그인이 필요하며 다중 앱 인스턴스 운영은 지원하지 않는다.
- 휴면·탈퇴 개인정보 삭제, 보관 기간 만료 삭제, 백업 삭제 이력 재적용은 아직 운영 절차로 처리해야 한다. WITHDRAWN은 접근 차단 상태이며 개인정보 삭제 완료를 뜻하지 않는다.
- 가족별 쿼터·추첨·결제·다중 숙소는 제외한다. 제한은 계정 기준이다.
- 관리 목록은 200~500건으로 제한된다. 점검은 활성 상태를 우선 표시하고, 연락·확인은 미처리의 오래된 건부터 표시하므로 처리하면 다음 건이 나타난다. 월 캘린더의 기간 조회에는 이 제한을 적용하지 않는다. 장기간 운영 시 페이지 나누기와 아카이브 화면을 추가한다.
- 정원 이외의 제안 규칙(90일, 연속 3일, 진행·미래 2건)은 가족 합의 후 설정을 확정한다.
- 관리자 추가 인증, 외부 상태 감시, 실제 백업 복원과 AWS 배포는 코드 테스트와 별도 승인 기준이다.
